## Context

见 `proposal.md` 的 Why。理解本设计需要以下现状约束：

- `bct/trade.php` 是「城市 = URL 参数」驱动的单条发布页，切换城市会整页刷新（`window.location.href = 'trade.php?city=...'`），因此批量模式不能用现有城市选择器作为主流程。
- `bct/process_order.php` 是单条发布的服务端入口，直接读取 `$_POST` 后调用 `BCTOrder::createOrder()`，校验逻辑与页面强耦合（失败即 `Location` 跳回 `trade.php?city=`）。
- `BCTOrder::createOrder()` 是单条原子操作：`beginTransaction → INSERT → commit`，异常时 `rollBack` 并返回 `false`。**它天然适合作为批量编排的最小单元**。
- `bct/admin/city_prices.php` 已实现同格式批量解析（约 13-93 行），规则与本变更要求一致，但解析逻辑内联在页面里、且语义是「改价」而非「建单」。
- `cities` 表同时承载真实城市与自建城市/品牌词条（见 `CityBCT::getAllCitiesBCT()` 注释），自建城市（如「鲸探」）就是普通行，无需新机制。
- `bct_orders` 有 `trade_type enum('platform','mediator','direct')`、`mediator_id`、`contact_info`、`amount int(11)`、`total_amount decimal(10,2)`，结构可容纳本次需求，无需迁移。

## Goals / Non-Goals

**Goals:**

- 在不破坏现有单条发布的前提下，为 `bct/trade.php` 增加批量模式。
- 解析、校验、提交三段职责分离，使「识别」可为纯读操作、可安全重复调用。
- 复用已有解析规则与 `createOrder()` 事务语义，避免引入新的订单创建路径。
- 让预校验结果与提交结果使用同一套状态语义，避免出现「预览说通过、提交却以另一种原因失败」的认知落差。

**Non-Goals:**

- 不重构单条发布为批量通道（单条仍走 `process_order.php`）。
- 不为批量引入 `platform` 交易或自动撮合（`autoMatchPlatformOrder()` 不在批量范围内）。
- 不提供「同城市不同价自动合并为加权均价」之类的价格干预。
- 不新增 `cities` 记录或「批量创建自建城市」能力。
- 不引入前端构建工具；沿用 CDN + 原生 jQuery 现状。

## Decisions

### 1. 解析逻辑抽为可复用组件，而非复制 `city_prices.php`

在 `classes/` 下新增批量订单解析器（如 `BatchOrderParser`），承载「文本 → 结构化行 → 错误分类」的纯函数式解析，`bct/admin/city_prices.php` 与批量发布共用同一份规则实现。

- **理由**：规则完全一致（全角空格、注释行、`\s+` 分列、三列约束）。复制一份必然产生规则漂移——将来任何一处调整都会造成两个入口行为不一致。
- **备选**：直接复制现有内联解析。实现更快，但留下长期维护债。
- **取舍**：抽取时需要顺带改动 `city_prices.php` 使其调用新组件，扩大改动面；接受该成本以换取单一规则来源。

### 2. 采用「预校验（只读）→ 提交（写入）」两阶段，两次都执行校验

预校验接口返回逐条状态但**完全不写库**；提交时对每条再次执行校验后立即 `createOrder()`。

- **理由**：预校验与提交之间用户可能停留较久，城市信息（如城市是否仍有效）可能变化。提交阶段复检是防止「预览通过但实际写入了不该写的订单」的必要防线。
- **备选**：信任预校验结果，提交阶段直接写库。实现更简单，但存在竞态窗口导致写入无效城市。
- **权衡**：两次校验意味着提交路径也要处理失败分支——这正是「部分成功」语义所要求的，因此不构成额外复杂度。

### 3. 合并键为「城市 + 价格」，累加发生在校验之前

先在解析产物上按 `(城市, 价格)` 归并数量，再进入校验。

- **理由**：累加后得到的数量才是该挂单最终的数量，数量上限校验必须针对累加后的值。
- **备选**：按城市合并（会把不同价的挂单错误地揉成一条）、或干脆不合并（与需求不符）。
- **顺序敏感**：归并必须先于数量校验，此顺序是正确性要求而非风格偏好。

### 3.1 不做余额校验（决策修正）

**原有判断被撤销**：初版设计将「卖单余额校验（按累加后数量）」作为批量必须新增的能力，依据是从单条模式代码推断「售出需校验余额」。但该推断与产品现状矛盾——发布交易页自身就提示「当前系统已简化流程，发布出售订单无需验证余额」。

因此本变更**彻底移除余额校验**，覆盖以下四处：

| 位置 | 处理 |
|---|---|
| 批量预校验接口 | 不再查 `user_bct_account`，不产出「可用余额不足」 |
| 批量提交复检 | 去除余额分支 |
| `BCTOrder::createOrder()` | 移除卖单余额校验与 `throw` |
| `bct/process_order.php`（单条） | 移除卖单余额校验 |

- **理由**：与既有产品行为保持一致，并使单条与批量口径统一。批量场景下要求同一用户的多个城市余额同时充足也不现实。
- **影响**：卖单可能超出账户余额被挂出；这是业务上已接受的现状（原单条流程同样如此，且发布时不扣减余额，交易完成时才处理）。

### 4. 批量提交以 `createOrder()` 为最小单元，逐条独立事务

每条挂单单独调用 `createOrder()`，天然获得「一条失败不影响其它条」的部分成功语义，无需在外层再包事务。

- **理由**：`createOrder()` 已自带事务与回滚，嵌套外层事务会让单条失败冒泡为整体回滚，直接违背需求中选定的「部分成功」。
- **备选**：外层统一事务（全或无）。与需求冲突，已排除。
- **代价**：无原子性保证，可能出现部分写入。这是需求明确接受的取舍，但要求结果必须逐条清晰反馈，否则用户无法判断哪些已发布。

### 5. 批量模式下 `mediator` 为整体选择，`platform` 不提供

- **理由**：批量行数多，逐行选中介不可用；`platform` 有 500 BCT 上限，与样例中 19000~65000 的数量级直接冲突，提供该选项只会制造「全部失败」的无效路径。
- **备选**：批量提供 `platform` 但超限行失败。表面上更「完整」，实则给用户提供了一条必然失败的路径。

### 6. 服务端统一上限常量 1000000

单条与批量共用同一上限值，并在服务端强制校验（补上 `process_order.php` 当前缺失的上限校验）。

- **理由**：前端 `max` 属性可被绕过，上限属于业务约束而非 UI 提示，必须在服务端生效。
- **备选**：仅改前端。不满足 `trade-publish-limits` 规格中的服务端校验要求。

### 7. 批量 UI 以模式切换内嵌于 `trade.php`，而非新建独立页面

- **理由**：两种模式共享「交易方式语义、联系方式、价格默认值」等概念，同页切换便于复用并对用户暴露完整心智模型；也避免用户在两处之间跳转导致的状态丢失。
- **备选**：独立 `batch_trade.php`。页面更简单，但重复承载交易方式/联系方式等概念。

## Risks / Trade-offs

- [Risk] 预校验通过后提交时城市信息被并发变更，导致「预览显示可发布、提交却失败」→ Mitigation: 提交阶段逐条复检并在结果中明确标注失败原因，把差异解释清楚而非静默失败。
- [Risk] 抽取解析器需同步改动 `city_prices.php`，可能影响现有管理端批量改价功能 → Mitigation: 抽取后保持 `city_prices.php` 的输出四分类（updated/skipped/missing/invalid）与行为完全不变，作为回归检查点。
- [Risk] 大批量行数（数十至上百条）逐条 `createOrder()` 产生多次数据库往返，页面响应变慢 → Mitigation: 明确批量规模预期；若实测超时，可后续在提交阶段做分批与进度反馈，当前不预先优化。
- [Risk] 城市按拼音匹配可能存在重名/歧义（多个城市拼音相同）→ Mitigation: 与 `city_prices.php` 现有行为保持一致（取 `LIMIT 1`）；若出现歧义引发的错配投诉，再引入显式歧义提示。
- [Risk] 上限从 100000 提升到 1000000 后单笔金额显著放大，且已不校验余额，理论上可挂出远超持仓的卖单 → Mitigation: 接受该现状（与既有单条流程一致，发布不扣减余额、交易完成时才处理）；在 UI 文案中明确上限已变更。
- [Risk] 用户粘贴文本中混入买卖方向信息（例如「买 吐鲁番 65000 0.03」）会因列数不符被归为无效行 → Mitigation: 在上限与格式提示文案中明确「方向由页面整体选择，每行仅三列」，降低误用概率。
