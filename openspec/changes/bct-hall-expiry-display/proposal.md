# Proposal: bct-hall-expiry-display

## What Changes

- **有效期列改为剩余时长**：挂单大厅「有效期」列从绝对时间点（`07-31 14:00`）改为相对剩余时长，按紧急度分级着色（>7 天灰 / 3-7 天黄 / 1-3 天橙 / <1 天红按小时）
- **长期单保留「长期」显示**（现状）
- **交易中顺延标识**：接单保护导致原有效期已过、仅因交易中存续的直接交易单，显示「交易中顺延」（悬停说明：仅冻结不续期）
- **个人中心「我的挂单」新增有效期列**：与大厅同口径；已完成 tab 显示「已结束」
- **已过期不显示**：由现有惰性过期 + 状态过滤保证（无回退即可，无代码改动）
- 纯展示层：新建一个公共格式化函数，两页复用；数据层零变更、无 SQL 迁移

## Capabilities

### New Capabilities
- `bct/trading/expiry-display`: 挂单剩余有效期的分级展示与交易中顺延标识规则

### Modified Capabilities

（无——挂单大厅与个人中心的展示尚未建立既有 spec，本变更为该能力首次建 spec）

## Why

- 现在显示 `07-31 14:00` 这类绝对时间，用户要自己心算还剩几天；挂单默认 30 天有效期，剩余天数才是决策信息（要不要降价、要不要赶紧接）
- 接单闭环上线后，`expireOverdueOrders` 对有活跃 claim 的订单做了跳过保护——交易中的单 `expires_at` 过了也不会消失，用户会疑惑"这单怎么 40 天了还挂着"

## Scope

**In scope**
- `bct/orders.php` 有效期列改为剩余有效期（含交易中顺延）
- `bct/user/dashboard.php` 我的挂单表新增有效期列（同口径）
- 纯展示层改动，数据层零变更（不改 `expires_at` 语义、不新增 SQL 迁移）

**Out of scope**
- 有效期筛选（只看长期/即将到期）——当前数据量下无需求，避免过度设计
- `buyer_confirmed` 卡单的申诉/撤销通道（后续独立变更）
- API/JSON 接口改造（列表是服务端渲染）

## Impact

- Files: `bct/orders.php`、`bct/user/dashboard.php`
- Risk: 低——展示逻辑，无状态流转变更；最坏情况是显示文案不符合预期
