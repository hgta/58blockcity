## Context

见 `proposal.md` 的 Why。理解本设计需要以下现状约束：

- `cities` 表已含 `bct_base_price` / `bct_current_price` / `bct_price_updated`，且 `CityBCT::updatePrice($city, $newPrice)` 是**所有改价途径的唯一收口**（`bct/admin/city_prices.php` 单行保存与批量设置、`CityBCT::autoAdjustPrice()` 自动调价）。
- `get24hChanges()` 现从 `bct_transactions` 按「24h 内最新 vs 24~48h 内最新」计算，并在 `prev_price` 缺失时用 `COALESCE` 回退为 `current_price`（结果为 0）。
- `bct_transactions` 仅由 `BCTOrder::executeTrade()` 写入，而 `executeTrade()` 只被 `platform` 类型订单的撮合调用；平台交易限 500 BCT，而用户实际发布 19000~65000 量级挂单，因此该表始终为空。
- **项目已有同类重构先例**：`archive/2026-09-08-city-prices-pagination` 将原 `city_bct` 独立表的单价物理并入 `cities`，理由是「单一事实源」，以消除 421 城市中仅 94 个有行情的断层。
- `bct/index.php` 与 `bct/market.php` 在**遍历 421 个城市的循环**内调用 `getCity24hVolume()`（N+1 模式已存在），因此新增的批量取数方法必须避免加剧该模式。
- 架构记录中 `bct-exchange-redesign/design.md` 曾写明：「价格历史通过 `bct_transactions` 聚合生成……**替代方案：新增 `city_price_history` 表存储分时数据。长期更优**，但本次范围优先复用现有数据。」——本次即是启用该「长期更优」方案。

## Goals / Non-Goals

**Goals:**

- 让涨跌城市、涨跌榜、24h 高低价、价格走势四个指标**立刻有真实数据**。
- 回到项目既有的「单一事实源」原则，消除两套价格来源的割裂。
- 埋点集中在唯一收口处，后续新增改价途径不遗漏。
- 保持批量取数特性，不引入按城市逐个查询的开销。

**Non-Goals:**

- 不修复成交量类指标（`getCity24hVolume()`、`getRecentTrades()`、走势图成交量柱）——它们需要真实成交事件，另案处理。
- 不重构 `autoAdjustPrice()` 的供需算法（只看订单笔数、不看数量、0/0 判为供给过剩等缺陷另案处理）。
- 不改动 `bct_current_price` 的写入逻辑与调价规则。
- 不新增价格历史的自动清理机制。
- 不改动页面模板，取数逻辑集中在 `CityBCT` 内。

## Decisions

### 1. 新增价格历史表，而非在 `cities` 上加「上一价」快照列

- **理由**：快照列只有「当前 vs 上一次」两档，涨跌幅语义随调价频率漂移（一天调价 20 次则反映最近两次差异，一周调价 1 次则变成一周涨跌），而首页文案是「涨跌城市」，用户理解的是 24 小时尺度。历史表可精确表达时间范围。
- **备选**：`cities` 增加 `bct_prev_price` + `bct_prev_price_at` 两列。改动更小，但语义不稳定。
- **一致性**：该方案正是架构记录中被标注为「长期更优」的替代方案，且与 `archive/2026-09-08` 的单一事实源原则同向。

### 2. 埋点放在 `updatePrice()` 内

- **理由**：`updatePrice()` 是所有改价途径的唯一收口，一处埋点即可覆盖后台单行保存、后台批量设置、自动调价三条路径。若放在各调用方，新增途径时极易遗漏。
- **备选**：各调用方分别记录。能区分「谁改的价」，但覆盖完整性靠人工维护，风险高。
- **取舍**：牺牲「变更来源」的可追溯性，换取覆盖完整性。若将来需要审计变更来源，可再给历史表加来源字段。

### 3. 涨跌幅采用「时间点对齐」而非「区间窗口」

- **理由**：原实现要求前价落在 `[NOW-48h, NOW-24h]` 区间内，若某城市在该窗口内恰好没有记录（例如 3 天未调价），前价取不到，城市被静默丢弃——这正是当前指标失真的机制之一。时间点对齐改为「取 24 小时前及更早的最后一条」，只要有更早记录就能参与统计。
- **备选**：沿用区间窗口。改动小，但会持续丢失样本。
- **代价**：涨跌幅的含义从「两个窗口内最新价的差异」变为「最新价相对 24 小时前价格的差异」，语义更贴近用户直觉。

### 4. 当前价在 24h 内无记录时回退为「最新一条历史」

- **理由**：某城市 24 小时未调价，说明价格**没有变化**，此时当前价理应等于那条未变的价格，而非"无数据"。若不回退，这类城市会从统计中消失，首页数字仍会显著偏小。
- **备选**：不回退，将无 24h 内记录的城市排除在统计外。与现状一致，但样本长期偏少。
- **边界**：完全无任何历史记录的城市仍不参与统计（无法判断涨跌）。

### 5. 批量取数，不在循环中按城市查询

- **理由**：`index.php` 与 `market.php` 对 421 个城市逐个取 `change_pct`。若 `get24hChanges()` 改为按城市查询，会从 1 次查询膨胀为 421 次。
- **实现**：`get24hChanges()` 保持「一次查询返回全部城市的 `city => change_pct` 映射」的契约；时间点对齐在**单条聚合 SQL** 内完成（每个城市分别取"最新一条"与"24h 前最后一条"），避免 PHP 侧循环单查。
- **注意**：既有的 `getCity24hVolume()` 的 N+1 问题本次不动（不在范围内），但新增代码不得沿用该模式。

### 6. 迁移脚本补初始快照

- **理由**：历史表只在改价时写入。若不做初始化，上线后需等 24 小时以上才可能有前价，指标将长期为 0，无法立即验证修复效果。为存量城市各补一条以当前价为准的快照，使数据立即就绪。
- **实现**：沿用 `init/migration-city-popularity-fields.sql` 的幂等风格（`information_schema` 检查 + 可重复执行），避免重复插入初始快照。
- **局限**：初始快照只有一个时间点，因此上线初期「24 小时前最后一条」仍可能取不到；此时按决策 4 回退，涨跌幅为 0（统计为持平）。真正有意义的涨跌需等待实际调价产生前后两个时间点。这是无法用迁移完全规避的客观限制，接受。

### 7. `getPriceHistory()` 的 volume 返回 0 并注明原因

- **理由**：成交量必须来自真实成交（`bct_transactions`），而该表为空。用「调价次数」或「价格波动幅度」冒充成交量会误导用户。
- **备选**：继续从 `bct_transactions` 取。结果同样是 0，但会让读者误以为数据源正确、只是暂无成交，掩盖「该表结构性为空」的事实。
- **做法**：显式返回 0，并在代码中注明待成交流水机制建立后接入。

## Risks / Trade-offs

- [Risk] 历史表长期无清理，数据量随时间增长 → Mitigation: 已确认不设自动清理（长期保留）；写入门槛是「价格发生变化时」而非定时快照，实际增长取决于调价频率，通常远低于按城市定时的量级。
- [Risk] 初始快照只有一个时间点，上线初期涨跌幅仍可能为 0 → Mitigation: 已在决策 6 中说明为客观限制；随实际调价发生，前后时间点齐备后指标自然生效。
- [Risk] 埋点在 `updatePrice()` 内，若历史表写入失败可能影响改价本身 → Mitigation: 历史写入应以「不影响主流程」为原则（记录失败不阻断价格更新），实现时需明确该容错边界。
- [Risk] 时间点对齐口径改变了涨跌幅语义，可能与此前观察到的数值不可直接比较 → Mitigation: 原数值恒为 0，不存在可比性损失；在代码注释中说明新口径。
- [Risk] 若调价频繁（如自动调价每轮触发），历史表会快速积累同价重复记录 → Mitigation: 可考虑仅在价格实际变化时写入；实现时确认自动调价在价格未变时是否仍调用 `updatePrice()`，若是则加去重判断。
- [Risk] 页面对 `change_pct` 的消费假设「一定存在该城市键」，改为无记录城市不返回后可能触发未定义索引 → Mitigation: 各消费方现均使用 `?? 0` 兜底（如 `$changes[$city] ?? 0`），保持该契约不变。
